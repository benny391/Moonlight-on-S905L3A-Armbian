# 开机花屏：定位过程与结论

## 现象

CM311-1A 接 Sony 电视，每次开机（冷启动**和热重启都**会出现）先显示几秒花屏/噪点，然后才出正常画面。期间电视有时会切到错误的 HDMI 输入。

## 结论（TL;DR）

**花屏与盒子/内核无关，是这台电视对启动早期 HDMI 信号的响应差异。** 证据是同一台盒子、同一套系统：

| 显示设备 | 输出模式 | 花屏 |
|---|---|---|
| Sony 电视 | 3840x2160@60 | 花 |
| Sony 电视 | **强制 1920x1080@60** | **花** |
| 普通 1080p 显示器 | 1920x1080@60 | **不花** |

换显示器就消失，换分辨率（同电视）不消失 → 变量是「电视本身」，不是分辨率、不是冷/热启动、不是内核 framebuffer。

因此**不对 U-Boot 或内核做任何改动**——那些都是高风险（重编内核 / 换 bootloader 有救砖风险），而花屏只是几秒的纯视觉现象，不影响串流质量与延迟。

## 定位过程（按时间顺序）

1. **最初猜测：U-Boot 阶段的 HDMI PHY/PLL 锁定。**
   推翻：CoreELEC（U 盘系统）共用同一个 boot0（`/dev/mmcblk2boot0` 里的 `U-Boot 2015.01-g23d25cc-dirty`），却在同电视上不花。若花屏在纯 U-Boot 阶段，CoreELEC 不可能幸免。

2. **修订猜测：主线 meson-drm 接管时把未清零的 framebuffer 亮出来。**
   CoreELEC 用厂商 4.9 显示栈把这段藏住了；主线 5.15 更早开启输出。网上有流传的「清 framebuffer」补丁，但经验证是 **ChatGPT 伪造**——它调用的 `drm_fb_vmap()` / `drm_fb_vunmap()` 在 5.15 头文件里根本不存在（真实 API 是 `drm_gem_shmem_vmap()` 等）。放弃照搬。

3. **低风险尝试：强制 4K60 输出模式**（`video=HDMI-A-1:3840x2160@60`）。
   结果：**花屏没解决，反而导致冷启动 HDMI 无信号**（connected 但 modeset 不成功，电视锁不住）。已回滚。

4. **关键实验：换 1080p 显示器。**
   盒子自动降到 1080p60，**完全不花**。首次把怀疑从「盒子」转向「电视」。

5. **补充线索：热重启也花。** 排除「PLL 冷锁」解释——热重启不彻底断电、PLL 有残留却仍花，说明是每次 DRM 初始化都发生、稳定复现的现象（之前「有一次没花」应是电视当时没盯着这个 HDMI 口）。

6. **交叉实验：强制电视跑 1080p**（`video=HDMI-A-1:1920x1080@60`，确认参数生效且实跑 1920x1080@60）。
   结果：**仍然花**。彻底排除「4K60 模式太苛刻」的猜测，坐实变量是显示设备。

## 为什么这个结论是合理的

花屏是盒子在启动阶段往 HDMI 线上输出、电视去锁定并显示出来的。盒子侧的早期信号两只显示器收到的应该是一样的——如果真是「未清 framebuffer」，1080p 显示器也会花。它没有，说明那段信号本身没有「可清理的垃圾」，差异在电视如何响应（何时去锁信号、锁定过程中的呈现方式）。

至于 CoreELEC 为何不花：更可能是它的显示初始化时序 / 输出模式切换时机恰好避开了这台电视的敏感窗口，而非输出内容不同。属于电视与特定信号时序的兼容问题。

## 实用的规避方向（都不改盒子）

- 换一根质量好的 HDMI 线，或换电视上另一个 HDMI 口
- 电视设置里关闭「HDMI 增强 / 快速切换」之类会频繁重锁信号的选项
- 开机前把电视切到别的输入，等盒子出图稳定后由 CEC 自动切回（本项目的 `cec-tv-wake` 已有切端逻辑，它等 `mesondrmfb` 出现后才切）

## 尝试过并已回滚的改动

| 改动 | 结果 | 状态 |
|---|---|---|
| 隐藏 `/boot/boot.bmp` logo | 无效（花屏不是 logo 图片） | 保留（无害） |
| 删 `console=tty0`（`uEnv.txt.bak-notty0`） | 无效 | 保留（无害） |
| `video=HDMI-A-1:3840x2160@60` | 花屏没解决 + 冷启动无信号 | **已回滚** |
| `video=HDMI-A-1:1920x1080@60` | 电视仍花 | **已回滚** |

## 附：想继续深挖的话

要 100% 坐实「盒子早期输出两只显示器收到的一致」，可以用 HDMI 采集卡分别录两台显示设备接收到的早期信号做逐帧对比。但对一个「几秒、纯视觉、不影响串流」的现象，投入产出比极低，不建议。
